# SmartKB 私有化部署文档

## 一、交付物清单

| 交付物 | 说明 |
|--------|------|
| 源码包（本仓库） | 后端 .NET 10 + 前端 Vue3 |
| `docker-compose.yml` | 一键启动：PostgreSQL(pgvector) + API + Web(Nginx) |
| `.env.example` | 环境变量模板（复制为 `.env` 修改） |
| `docs/方案设计.md` | 架构与里程碑说明 |

客户服务器要求：**4C8G 起**（建议 8C16G），已安装 Docker 与 Docker Compose 插件。LLM 走 Local 模式时另需 Ollama 服务或 GPU 机器。

## 二、部署步骤

```bash
# 1. 解压源码包，进入仓库根目录
cp .env.example .env
vi .env        # 修改数据库密码、JWT 密钥、管理员初始密码、LLM 配置

# 2. 一键构建启动（首次约 5-10 分钟拉镜像构建）
docker compose up -d --build

# 3. 查看状态与日志
docker compose ps
docker compose logs -f api     # 看到 Seed 完成即启动成功
```

启动完成后访问 `http://<服务器IP>/`（端口由 `.env` 的 `WEB_PORT` 决定），用 `admin` + `ADMIN_INITIAL_PASSWORD` 登录。

## 三、上线必改配置（`.env`）

| 变量 | 说明 |
|------|------|
| `POSTGRES_PASSWORD` | 数据库强密码 |
| `JWT_SECRET_KEY` | ≥32 字符随机串（`openssl rand -base64 48`） |
| `ADMIN_INITIAL_PASSWORD` | 管理员初始密码，**首次登录后立即在系统里改掉** |
| `LLM_MODE` | `Agnes`（默认，Agnes AI）/ `Cloud`（智谱云 API）/ `Local`（内网 Ollama） |
| `LLM_AGNES_API_KEY` | LLM_MODE=Agnes 时必填（对话模型） |
| `LLM_API_KEY` | 智谱 API Key：LLM_MODE=Cloud 时为对话 Key；LLM_MODE=Agnes 时仅用于向量化（必填）；Local 时留空 |
| `TOOLS_ALLOWED_HOSTS` | 选填：配置化 Agent 工具的目标主机白名单，建议生产开启；客户业务系统密钥按变量名单独注入，见三之五 |
| `GATEWAY_ENABLED` / `GATEWAY_API_KEY` / `GATEWAY_SERVICE_USERNAME` | 选填：OpenAI 兼容网关，**默认关闭**，三者必须齐备；详见三之六 |
| `LDAP_*` 全套 | 选填：LDAP/AD 可选登录，**默认关闭**；详见三之七 |
| `OCR_ENABLED` / `OCR_ENDPOINT` / `OCR_API_KEY_ENV` | 选填：OCR sidecar，**默认关闭**；详见三之七 |
| `QUEUE_MODE` | `Memory`（默认，单实例）/ `Database`（多实例安全）；**api 多实例部署必须切 Database**，详见三之七 |

## 三之二、安全与存储（v1.1）

| 项 | 说明 |
|---|---|
| CORS | 生产由 Nginx 同源反代，**默认不开放任何跨域来源**。若前端独立域名部署，在 `src/SmartKB.Api/appsettings.json` 配 `SmartKB:CorsAllowedOrigins`（数组）；切勿用通配符配合 AllowCredentials |
| 文件存储 | `docker-compose.yml` 固定 `SmartKB__FileStoragePath=/app/storage`，对应 `kbstorage` 卷。**键名必须与代码一致**（代码读 `SmartKB:FileStoragePath`），写错会使文件落进容器可写层，容器重建即丢 |
| 对象级授权 | 服务层强制校验知识库 `Manage` 权限，越权返回 HTTP 403；`kb_manager` 只能管理被授予 Manage 的库，不能跨库传/删文档或自我授权 |
| 自动迁移 | 启动时执行 EF 迁移与种子；升级前先备份数据库 |
| 多实例 | 进程内 Channel 文档队列不支持多实例（会重复消费），按单机交付 |

## 三之三、RAG 运行时配置（v1.2）

问答行为参数**不需要改配置文件、不需要重启**：登录管理后台 →「RAG 配置」（仅管理员可见），修改后保存，后续问答立即生效。配置覆盖值存数据库 `sys_settings`（键前缀 `rag.*`），`appsettings.json` 的 `RAG` 节作为默认基线，「恢复全部默认值」会删除全部覆盖记录。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `rag.system_prompt` | 内置约束提示词 | 改 Agent 行为，最长 8000 字符 |
| `rag.top_k` | 8 | 最终进入上下文的分块数（1–30） |
| `rag.candidate_top_k` | 24 | 融合/重排前的候选池（1–100），须 ≥ top_k |
| `rag.hybrid_enabled` | **false** | 混合检索：向量 + PostgreSQL 全文/中文精确词双路，RRF 融合；关闭即纯向量 |
| `rag.metadata_filter_enabled` | true | 按知识库字段 schema 中 `filterable` 的字段过滤文档 |
| `rag.rerank_enabled` | **false** | 融合后二次排序 |
| `rag.rerank_provider` | `Heuristic` | `Heuristic`（零依赖）/ `Api`（外部 rerank 模型） |
| `rag.rerank_top_n` | 12 | 参与重排的候选数（1–50） |
| `rag.temperature` | 0.2 | 生成温度（0–2） |
| `rag.max_output_tokens` | 2048 | 单次回答上限（128–32768） |

两个「默认关闭」的开关是刻意留的回退阀：客户语料以精确编号/型号为主时开混合检索 + 重排收益明显；若召回反而变差，关掉即可回到纯向量，不用发版。

**全文索引迁移**：混合检索的关键词路由迁移 `20261105010811_AddChunkFullTextIndex` 在 `kb_chunks.Content` 上创建**表达式 GIN 索引**（不改变表结构、不改 EF 模型，SQL 表达式与索引严格一致才命中）。升级时 EF 启动自动迁移会建索引；存量分块较多时建索引可能耗时数十秒到数分钟，建议在低峰期升级。索引缺失时混合检索仍能工作，只是关键词路退化为全表计算。中文 `ILIKE '%词%'` 兜底目前仍是顺序扫描，超大规模语料可再评估 `pg_trgm`。

**元数据过滤前置条件**：在「知识库管理 → 字段配置」里给需要过滤的字段勾上「可过滤」，且文档上传时按该字段名写入 `metadataJson`。字段名与操作符均过服务端白名单，LLM 只能产参数，不能产 SQL。

**外部重排密钥（选填）**：选 `Api` 重排时在 `.env` 配 `RERANK_API_KEY`（compose 映射为 `RAG__Rerank__Api__ApiKey`），可一并改 `RERANK_BASE_URL` / `RERANK_MODEL`。密钥**只允许环境变量注入**，不要写进 `appsettings.json`。未配置密钥或外部接口报错时自动降级为零依赖的启发式重排，并在日志里留 Warning，问答不会中断。

**多实例说明**：配置缓存为进程内 10 秒 TTL，保存时本实例立即失效，其他实例最多延迟 10 秒生效（当前按单机 Compose 交付，不受影响）。

## 三之四、审计日志与探活（v1.3）

**操作审计**：`sys_audit_logs` 表由迁移 `20261105011823_AddAuditLog` 创建（启动自动迁移）。全局过滤器记录所有 `/api` 写操作：登录、用户/角色/知识库/文档/授权、配置变更，含操作人、语义化动作、路径、状态码、耗时、IP/UA、失败原因。管理后台「审计日志」（仅管理员）支持按分类、成败、时间范围、关键字筛选与分页。

| 项 | 说明 |
|---|---|
| 脱敏 | **只记元数据，不记请求体与响应体**——密码、ApiKey、文档正文不会入库；GET 请求不记录，避免文档状态轮询刷屏 |
| 来源 IP | 优先取 `X-Forwarded-For` 第一段（Nginx 反代场景），该头可伪造，仅作参考 |
| 失败容错 | 审计写入用独立 DI scope，失败只写日志、不影响业务请求结果 |
| 保留策略 | 表随写操作持续增长，系统**不做自动删除**。按客户合规要求定期归档或清理，例如保留 180 天：`DELETE FROM sys_audit_logs WHERE "CreatedAt" < now() - interval '180 days';`（执行前先备份） |

**分项探活**：`GET /health` 匿名可访问，供 Nginx / 网关 / K8s 探活或运维排障。返回 `{ status, db, checkedAt, checks[] }`。

| 分项 | 检查内容 | 故障时 |
|---|---|---|
| `database` | 数据库连通性 | `unhealthy` → **HTTP 503** |
| `pgvector` | `vector` 扩展、HNSW 向量索引、全文 GIN 索引是否存在 | `degraded` → HTTP 200 |
| `storage` | `SmartKB:FileStoragePath` 目录可创建并写入临时文件 | `unhealthy` → **HTTP 503** |
| `llm` | 按 `LLM_MODE` 探 `/models`（Agnes/Cloud）或 `/api/tags`（Local），3 秒超时 | `degraded` → HTTP 200 |

- **LLM 抖动只降级不判死**：外部 API 临时故障不应让编排器反复重启容器。用 `/health` 做 liveness 时建议区分 readiness（只看 `status != unhealthy` vs 同时要求 `healthy`）。
- 结果缓存 **10 秒**，避免监控每 5 秒探一次就把厂商 `/models` 打限流；故障最多延迟 10 秒反映。
- 密钥只用于发请求，**绝不回显**在 `checks[].detail`；非关系型 provider（单测）标 `skipped`。
- 保留旧字段 `{ status, db }`，老监控规则不会失效。

## 三之五、配置化 Agent 工具（v1.4）

`sys_agent_tools` 表由迁移 `20261105014246_AddAgentTools` 创建（启动自动迁移）。管理后台「工具注册表」（仅管理员）登记内部 HTTP 接口后，模型在问答时按需调用，无需改代码发版。

### 1. 主机白名单（建议生产开启）

```env
# .env —— 逗号或分号分隔，可写 host 或 host:port
TOOLS_ALLOWED_HOSTS=erp.internal;crm.internal:8443
```

对应 compose 已接好 `Tools__AllowedHosts: ${TOOLS_ALLOWED_HOSTS:-}`。**留空 = 信任后台登记的任何 http/https 地址**；填了之后，保存工具时 host 不在白名单会直接被拒，运行时加载也会再次校验。私有化交付建议按客户内网域名锁死，避免管理员误配到公网。

### 2. 密钥注入（最容易踩的坑）

后台「鉴权」只填**环境变量名**（如 `ERP_API_TOKEN`），绝不把 Token 写进数据库。密钥由运维在服务端注入：

```env
# .env
ERP_API_TOKEN=客户提供的真实Token
```

```yaml
# docker-compose.yml → services.api.environment 必须显式加一行，否则 .env 的变量不会进容器
ERP_API_TOKEN: ${ERP_API_TOKEN:-}
```

改完 `docker compose up -d` 重启 API 生效。后台列表的「密钥」列会显示 **已配置 / 未配置**（只回显布尔值，不回显内容）；未配置时工具调用返回可读提示，不中断问答。

> 非 Docker 部署：在 API 进程的操作系统环境变量里设置同名变量即可（Windows 需重启服务进程）。

### 3. 登记示例

| 字段 | 值 |
|---|---|
| 函数名 | `query_device_status` |
| 描述 | 按设备编号查询设备当前运行状态、最近保养时间；用户问「某设备现在什么状态」时调用 |
| HTTP 方法 / URL | `GET` · `https://erp.internal/api/device/{device_no}?year={year}` |
| 参数表 | `device_no`(string/path/必填) · `year`(string/query/选填) |
| 鉴权 | 头 `Authorization` · 变量名 `ERP_API_TOKEN` · 前缀 `Bearer ` |
| 限制 | 超时 8 秒 · 响应上限 4000 字符 |

保存后用「试运行」填 `device_no` 验证连通性与返回格式，再到聊天里问一句自然语言确认模型会调用。**试运行会真实请求上游，请只登记只读接口**；POST 工具的请求体模板里占位符写 `{param}`（不带引号），服务端自动做 JSON 转义。

### 4. 边界与排障

- v1.5 起可在工具行点「授权」设置**用户/角色白名单**：不选 = 公开，选中 = 仅这些对象与管理员可用（网关的服务间调用同样按绑定账号过滤）。v1.6 再补**知识库范围**：限定工具只服务于特定知识库，问答范围与其无交集时本次不注入。
- URL 的域名来自模板，参数只进 path/query/body 且被 URL 编码，模型改不了目标主机；3xx 重定向不跟随，防止绕过白名单。
- 同时最多启用 20 个工具（控制 prompt 体积）；保存后新问答立即生效，进程内缓存 10 秒 + 保存主动失效。
- 工具返回空或报「工具调用失败」时：先看 API 日志的 Warning（含异常），再核对白名单、密钥环境变量、上游超时与非文本内容类型（二进制响应会被忽略）。

## 三之六、OpenAI 兼容网关（v1.5，选填，默认关闭）

客户已有 ChatGPT 客户端、OA/CRM 或自研系统可直接用 OpenAI SDK 接入，不必改造 SignalR。**默认关闭**，`/v1/*` 在未启用时返回 OpenAI 格式的 503。

### 1. 启用步骤

1. 在管理后台「用户管理」创建一个**专用服务账号**（如 `svc_openai`），按需要授权知识库。**不要直接用 admin**——否则这把 Key 能读全部知识库、调用全部工具。
2. 在 `.env` 里配齐三项（缺一不可）：

   ```ini
   GATEWAY_ENABLED=true
   GATEWAY_API_KEY=<强随机字符串，例如 openssl rand -base64 48>
   GATEWAY_SERVICE_USERNAME=svc_openai
   # 默认忽略请求里的 system 消息，统一由后台「RAG 配置」管控
   GATEWAY_ALLOW_SYSTEM_PROMPT=false
   ```

3. `docker compose up -d --build` 重启 API（compose 已把 `Gateway__*` 逐项注入容器；**`.env` 里的变量不会自动进容器**，新增变量必须同时在 `api.environment` 列出）。
4. 用 Nginx 对 `/v1/` 配置限流与访问来源限制——网关本身**不限流**。

### 2. 调用示例

```bash
# 列出可访问知识库（model = smartkb:{kbId} 可限定检索范围）
curl http://<host>/v1/models -H "Authorization: Bearer $GATEWAY_API_KEY"

# 非流式
curl http://<host>/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"smartkb:3","messages":[{"role":"user","content":"保修期多久？"}]}'

# 流式：加 "stream":true，返回标准 chat.completion.chunk SSE + data: [DONE]
# 需要末尾 usage：加 "stream_options":{"include_usage":true}
```

请求里的 `kb_ids: [3]` 优先级高于 `model`；两者都只是**请求范围**，服务端仍与 `GetAccessibleKbIdsAsync` 求交，指定无权库会返回可读错误。`session_id` 传已有会话（必须归属当前账号）可保持多轮；不传则新建 `[API] ...` 会话，高频调用需按服务账号定期归档。

### 3. 鉴权与返回

| 项 | 说明 |
|---|---|
| 静态 Key | `Gateway__ApiKey` 仅环境变量注入，SHA256 + 定长比较，不回显、不进日志；绑定到 `GATEWAY_SERVICE_USERNAME` 指定的真实账号 |
| JWT 兜底 | 也接受现有用户 JWT，按登录用户本人计算知识库与工具权限 |
| 错误格式 | `{ "error": { "message", "type", "code" } }`；未启用 503、鉴权失败 401、参数错误 400、上游异常 502 |
| 引用 | OpenAI 协议无引用字段，用扩展 `smartkb_citations` 返回（非流式在 `choices[0].message`，流式单独一个 chunk） |
| 观测 | 每次调用落会话、消息与 `ai_invocation_logs`，与 SignalR 共用「AI 观测」面板 |

**system 消息默认被忽略**（`GATEWAY_ALLOW_SYSTEM_PROMPT=false`），避免外部客户端覆盖企业的系统提示词；`temperature`（0–2）与 `max_tokens`（128–32768）允许请求覆盖并做范围校验。网关写请求不走全局审计过滤器（只覆盖 `/api`），靠会话与观测留痕。

## 三之七、文档级授权、LDAP、OCR 与多实例队列（v1.6）

### 1. 文档级授权

管理后台 → 知识库 → 文档行 → 「授权」：**一个都不选 = 跟随库权限**（本库内可读用户都能看到该文档，升级零迁移成本）；选中任意用户/角色后，仅这些对象与**库管理员**可检索到该文档。检索（向量 + 关键词两路）、台账查询与文档列表同时生效，Manage 权限与管理员不受限。写操作进审计 `set_document_grants`。注意：被限制的文档对普通用户"不可见"，但**不会**提示其存在——不要把授权当加密用，敏感内容仍应控制在上游文档本身。

### 2. LDAP/AD 可选登录（默认关闭）

```ini
# .env
LDAP_ENABLED=true
LDAP_SERVER=ad.corp.local          # 域控地址
LDAP_PORT=389                      # LDAPS 用 636 且 LDAP_USE_SSL=true
LDAP_USE_SSL=false
LDAP_BASE_DN=DC=corp,DC=local
LDAP_SEARCH_FILTER=                # 留空 = AD 默认 (sAMAccountName={0})
LDAP_BIND_DN=CN=svc_smartkb,OU=ServiceAccounts,DC=corp,DC=local
LDAP_BIND_PASSWORD=<服务账号密码，只走环境变量>
LDAP_DEFAULT_ROLE=普通用户          # 须为「角色管理」里已存在的角色名，留空则新账号无库权限
```

- 逻辑：本地密码**优先**；本地校验失败且 LDAP 开启时走 search-then-bind（绑服务账号 → 搜用户 DN → 以用户 DN + 用户密码二次绑定验证），通过即**自动开通**本地账号并挂 DefaultRole。自动开通的账号密码哈希是随机值，本地密码路径不可登录。
- **先在「角色管理」建好 DefaultRole 角色**，否则新账号无任何知识库权限，需管理员手动授权。
- 登录名做 RFC 4515 转义，域控不可达/凭据错只表现为「用户名或密码错误」，不暴露细节；排障看 API 日志的 LDAP Warning。
- 服务账号建议只读权限；密码轮换改 `.env` 重启即可。

### 3. OCR sidecar 可选接入（默认关闭）

客户自备 HTTP OCR 服务（如 PaddleOCR serving 部署在内网），系统在其不可用时不影响主流程：

```ini
# .env
OCR_ENABLED=true
OCR_ENDPOINT=http://host.docker.internal:8866/ocr   # POST multipart/form-data，字段名 file
OCR_API_KEY_ENV=OCR_API_KEY                         # 可选：值经 X-Api-Key 头发送，只登记变量名
```

触发条件：仅 PDF 且解析文本 < 120 字符（`Ocr:MinTextChars` 可调，疑似扫描件）。响应取 JSON 的 `text` 字段或纯文本，截断到 `Ocr:MaxTextChars`（默认 20 万字符）后进切分器。**未启用或调用失败维持原行为**——纯图片 PDF 仍标记 Failed，可在开 OCR 后用「重试」批量重跑。

### 4. 多实例文档队列

api 服务需要扩多实例（`docker compose up -d --scale api=N`）时，**必须**设 `QUEUE_MODE=Database`：

| 模式 | 机制 | 适用 |
|---|---|---|
| `Memory`（默认） | 进程内 Channel，重启自动恢复 | 单实例，零额外开销 |
| `Database` | PostgreSQL `FOR UPDATE SKIP LOCKED` 逐条认领 `kb_documents`，启动时崩溃遗留的 Parsing 文档自动放回队列 | 多实例；认领与状态推进在一条 SQL 内，不会重复消费 |

多实例部署还需前置负载均衡（Nginx upstream / K8s Service）；「RAG 配置」与探活结果缓存为进程内 10 秒 TTL，多实例间最多 10 秒收敛，属预期行为。web 容器仍是单实例静态站。

## 四、LLM 三种模式

**Agnes（默认）**：对话走 Agnes AI OpenAI 兼容接口（`https://apihub.agnes-ai.com/v1`，模型 `agnes-3.0-flash`）。Agnes 无 Embedding 模型，向量化自动回退智谱 `embedding-3`，因此需要同时配置 `LLM_AGNES_API_KEY` 与 `LLM_API_KEY`（智谱）。

**Cloud（云 API）**：默认智谱 OpenAI 兼容接口，对话与向量化全部走智谱，只需 `LLM_API_KEY`。数据（文档内容与问题）会发送到云端模型服务，适合可接受外部 API 的客户。

**Local（内网推理）**：客户内网部署 Ollama，拉取 `qwen3:14b` 与 `bge-m3` 模型，数据完全不出内网。容器访问宿主机 Ollama 时 `LLM_LOCAL_BASEURL=http://host.docker.internal:11434`。切换模式只改 `.env`，**不改代码不重建数据**（注意：Embedding 模型不同会导致向量不兼容，切换后需对文档重新向量化，用重试功能批量触发）。

## 五、数据备份

```bash
# 数据库备份（知识库、向量、台账、会话、sys_settings 配置覆盖、审计日志、工具注册表与授权、文档级授权全在这里）
docker compose exec db pg_dump -U smartkb smartkb > backup_$(date +%F).sql

# 恢复
cat backup_2026-09-22.sql | docker compose exec -T db psql -U smartkb smartkb
```

文档原文件在 `kbstorage` 数据卷，必须与数据库备份配套（缺一不可，否则恢复后无法下载原文 / 重新解析 / 引用定位）：

```bash
docker run --rm -v smartkb_kbstorage:/data -v "$PWD":/backup alpine \
  tar czf /backup/kbstorage_$(date +%F).tar.gz -C /data .
```

## 七、可观测

- 结构化日志：`docker compose logs api`（Serilog JSON）
- 全链路追踪：`.env` 配置 `OTLP_ENDPOINT=http://<collector>:4317` 后自动导出（HTTP 入站/出站 + Npgsql SQL），配 Jaeger/Tempo/Grafana 均可
- AI 调用观测：管理后台「AI 观测」——每次问答的 token 用量、首字延迟、总耗时、工具调用、命中数、成功/失败
- 操作审计：管理后台「审计日志」——谁在何时做了什么、状态码、耗时、来源 IP、失败原因
- 健康检查：`GET /health`（4 分项 + healthy/degraded/unhealthy 分级；`unhealthy` 返回 503，`degraded` 返回 200）

## 八、常见问题

| 现象 | 处理 |
|------|------|
| 文档状态一直"失败" | 查看失败原因列；扫描件 PDF 无文本层属预期（可按三之七开 OCR sidecar 后重试） |
| .doc/.xls 老格式解析失败 | 让客户另存为 .docx/.xlsx 再上传 |
| 回答报"生成中断" | 检查 `LLM_API_KEY` 或 Local 模式 Ollama 连通性 |
| 换了 Embedding 模型后检索异常 | 向量维度/语义空间变了，需对全部文档触发重试重新向量化 |
| 上传大文件失败 | Nginx 已放宽至 60m，检查是否有前置网关限制 |
| 开启混合检索后召回没变化 | 确认后台 `rag.hybrid_enabled` 已保存；关键词路依赖 PostgreSQL 原生全文检索，仅 pgvector 容器可用 |
| 升级后首次启动偏慢 | 全文 GIN 索引迁移在给 `kb_chunks` 建索引，存量分块多时耗时较长，属一次性；查 `docker compose logs api` 确认迁移完成 |
| 外部 Rerank 不生效 | 检查 `.env` 的 `RERANK_API_KEY` 与日志 Warning；密钥缺失或接口失败会自动降级启发式重排，不会中断问答 |
| 元数据过滤提示"字段未配置为可过滤" | 到「知识库管理 → 字段配置」勾选该字段的「可过滤」，并确认文档 `metadataJson` 里写了同名字段 |
| 想还原所有问答参数 | 后台「RAG 配置 → 恢复全部默认值」，会删除全部 `rag.*` 覆盖记录 |
| `/health` 一直报 `degraded` | 看 `checks[].detail`：常见是未配 LLM ApiKey、全文索引迁移未执行、LLM 端点 5xx。`degraded` 仍返回 200，不影响服务启动 |
| 审计日志表增长过快 | 按合规要求定期归档/清理 `sys_audit_logs`，见三之四；系统不会自动删除 |
| 工具试运行提示「鉴权未配置」 | `.env` 里设了变量还不够，必须在 compose 的 `api.environment` 显式列出该变量并重启 API，见三之五 |
| 后台保存工具提示「主机不在白名单」 | 检查 `TOOLS_ALLOWED_HOSTS` 是否漏了目标 host；留空则不限制 |
| 模型不调用新登记的工具 | 确认工具已启用、描述写清了业务场景；工具名不能与内置 `search_knowledge` / `query_ledger` 重名；若设了「授权」，确认当前用户/角色在白名单里（列表显示「受限」） |
| 调用 `/v1/chat/completions` 返回 503「网关未启用」 | `GATEWAY_ENABLED` / `GATEWAY_API_KEY` / `GATEWAY_SERVICE_USERNAME` 必须三项齐备，且 `api.environment` 已逐项注入并重启 API |
| 网关返回 401 | 检查 `Authorization: Bearer <Key>` 是否与 `GATEWAY_API_KEY` 完全一致；若用 JWT，确认未过期且签名密钥一致 |
| 网关返回 503「服务账号不存在或已禁用」 | 这是**配置错误**而不是 Key 填错：先在「用户管理」创建/启用 `GATEWAY_SERVICE_USERNAME` 指定的账号 |
| 系统提示词被外部客户端改了 | 默认忽略 system；确认 `GATEWAY_ALLOW_SYSTEM_PROMPT` 未被设为 `true` |
| 网关调用产生的 `[API]` 会话太多 | 服务端为新会话自动创建；可传 `session_id` 复用，或按服务账号定期归档 `chat_sessions` |
| LDAP 登录总提示「用户名或密码错误」 | 域控连通性（`LDAP_SERVER:PORT`）、服务账号密码、`LDAP_BASE_DN` 与过滤器；看 API 日志的 LDAP Warning（错误码 49 = 凭据错，其余为连接问题）。`LDAP_DEFAULT_ROLE` 不存在时新账号能登录但无库权限，需管理员手动授权 |
| LDAP 验证通过但新账号没有知识库权限 | `LDAP_DEFAULT_ROLE` 角色名不存在——先在「角色管理」建角色，或管理员手动给账号授权知识库 |
| 多实例部署文档重复处理/漏处理 | `QUEUE_MODE` 未切 `Database`；见三之七第 4 节。配置缓存与探活缓存多实例有最多 10 秒延迟属预期 |
| 某文档检索不到 | 先查文档状态是否 Indexed；再查是否被设置了文档级授权（知识库 → 文档 → 授权）且当前用户/角色不在白名单 |
